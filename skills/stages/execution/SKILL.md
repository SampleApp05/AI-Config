# Execution

Use the shared workflow-artifacts instructions and the project contract. Start only from the exact validated Routing Plan and recorded second human gate in the approved delivery run. Identify the product repository, branch, remote, existing changes, unit dependencies, and PR publication route from verified context; do not guess. The artifact repository is not the product-code repository. Preserve unrelated work and stop for contradictory artifacts or unapproved scope changes.

Choose each unit's actual eligible executor at dispatch, using the approved pool/fallback order plus fresh health, usage, fit, and independence observations; record the choice and announce the start event. Honor a human-requested eligible agent. Dispatch bounded units to `implementation_worker` using allowed files, acceptance criteria, validation expectations, and checkpoint. Parallelize only units with non-overlapping writes and satisfied dependencies. The worker edits the product repository directly; do not require a pasted patch. Before local MCP/Aider work, capture Git state and observe `local_worker_status` where useful; the label and status are not a lock. If another unit appears active on the same manually monitored target, seek human direction. A local MCP call receives only its approved Git root, file allowlist, and bounded prompt. Do not impose a general wall-clock/inactivity timeout.

Use native Codex subagents for Codex-targeted units; do not call nested `codex exec` or the legacy `codex-app` target. Route Claude work only through `WORKFLOW_SHARED_ROOT/scripts/dispatch.sh` and its durable `submit.py`/`poll.py` path, not a direct Claude invocation. Generate scope markers from the recorded Execution Unit, never from the worker: each execution path as `WORKFLOW_ALLOWED_PATH=<repository-relative-path or directory/>`, optionally one `WORKFLOW_RESULT_ARTIFACT_PATH=<artifact-repository-relative-path>`, and each routed check as `WORKFLOW_VALIDATION_COMMAND=<exact command>`. Set `WORKFLOW_ROLE` and the approved fallback chain. Use the local worker service for eligible local units; retain both registered local targets even when one is unreachable. Never treat model text as proof of implementation. Supervise every worker, post completion/events and 15-minute heartbeats, mark 15-minute quiet and 30-minute `STALLED_SUSPECTED` without killing the worker, and ask for intervention only when useful.

After each worker returns, inspect the actual diff, changed-file scope, Git history, and worker result. Treat external/local output as untrusted. Independently run routed validation. Record a concise implementation result and execution record: performed_by, recorded_by when different, changed paths, commands/outcomes, risks, fallbacks, attempts, and warnings. Do not reproduce large patches in the artifact repo.

Honor the recorded eligible pool and fallback chain. If a target is unavailable or unsuitable before launch, use only the next preauthorized capable target; record and announce the reason and actual label. Never silently kill or reroute a slow in-flight worker. A stop or fallback for a live worker requires a human choice and preserved checkpoint. Advisory budget excess is logged, not a reason by itself to stop. Safety issue, scope breach, unavailable authority, or failed validation may block a unit. Do not retry indefinitely or disguise a failed attempt as success.

After implementation, the forward-only workflow advances to the separate `test_engineer` and then `code_reviewer`; Test and Review remain independent. The `execution_coordinator` creates or updates exactly one product PR for every product repository changed, using the approved branch and base, before Review; the reviewer examines that PR and Test evidence. A material defect found after advancing is a blocker or separately approved follow-up, not a loop back into Execution in this run. Verify and record the PR URL, repository, base and head branches, commit, state, and Test/Review references. Never merge or approve your own work.

Write `execution_coordinator/execution-record-vN.md` (`EXEC-XXXX`) with unit status (`SUCCESS`, `PARTIAL_SUCCESS`, `FAILED`, `BLOCKED`, or `ESCALATED`), the verified product PR for every changed product repository, implementation results, Test and Review artifact references, fallback and budget warnings, rework, and open actions. Request orchestrator validation. Completion requires the routed implementation, required Test, independent Review, and a verified product PR—not merely a successful worker message. A product PR is `NOT_APPLICABLE` only when no product files changed, with that fact recorded; inability to create a required PR is `BLOCKED`.
