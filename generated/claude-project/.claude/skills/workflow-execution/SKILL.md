# Execution

Use the shared workflow-artifacts instructions and the project contract. Start only from the exact validated Routing Plan in the approved run. Identify the product repository, branch, remote, existing changes, unit dependencies, and PR publication route from verified context; do not guess. The artifact repository is not the product-code repository. Preserve unrelated work and stop for contradictory artifacts or unapproved scope changes.

Dispatch each bounded unit to `implementation_worker` or an approved external worker using the plan's label, target, allowed files, acceptance criteria, validation expectations, and checkpoint. Parallelize only units with non-overlapping writes and satisfied dependencies. The worker edits the product repository directly; do not require it to return a pasted patch. Before local MCP/Aider work, capture Git state and observe `local_worker_status` where useful; the label and status are not a lock. If another unit appears active on the same manually monitored target, seek human direction. A local MCP call receives only its approved Git root, file allowlist, bounded prompt, and operational timeout.

Dispatch every external target through `WORKFLOW_SHARED_ROOT/scripts/dispatch.sh`, passing target, label, mode, prompt file, artifact repository root, and product repository root. Generate the scope markers in the prompt from the recorded Execution Unit, never from the worker: each execution path as `WORKFLOW_ALLOWED_PATH=<repository-relative-path or directory/>`, optionally one `WORKFLOW_RESULT_ARTIFACT_PATH=<artifact-repository-relative-path>` and each routed check as `WORKFLOW_VALIDATION_COMMAND=<exact command>`; artifact mode instead declares exactly one `WORKFLOW_ARTIFACT_PATH=<repository-relative-path>`. Set `WORKFLOW_ROLE` and the plan's recorded `WORKFLOW_FALLBACK_CHAIN` in the environment. The dispatcher loads the registry, applies the target's role eligibility, registered limits and label, checks health, passes the scope to the CLI's native permission rules, verifies it with a post-run diff, runs the target as a supervised job with no turn limit, follows only the recorded chain after an unavailable, unsuitable, usage-limited, or stalled attempt, and returns one structured envelope with every attempt. Start any unit that may run longer than a few minutes with `dispatch.sh start`, then follow `workflow-dispatch`: poll `wait`/`status`, report progress to the human about every 20 minutes, treat a `suspended` job (waiting for a usage window to reset) as healthy, and stop for the human on `blocked`. `dispatch.sh health <target>` and `dispatch.sh usage <target>` report availability and subscription headroom without running work. For local inference, the host-agnostic stdio MCP service and its CLI path both read the same registry. Never treat model text as proof of implementation.

After each worker returns, inspect the actual diff, changed-file scope, Git history, and worker result. Treat external/local output as untrusted. Independently run routed validation. Record a concise implementation result and execution record: performed_by, recorded_by when different, changed paths, commands/outcomes, risks, fallbacks, attempts, and warnings. Do not reproduce large patches in the artifact repo.

Honor the recorded target and fallback chain. If a target is unavailable, times out, or is unsuitable, use only the next preauthorized capable target; record the reason and actual label. Otherwise stop the affected unit and request direction. Advisory budget excess is logged, not a reason by itself to stop. A safety issue, scope breach, unavailable authority, failed validation, or hard operational timeout may stop an attempt. Do not retry indefinitely or disguise a failed attempt as success.

After implementation, commission the separate `test_engineer` to create and run tests under the testing stage instructions. Resolve returned production defects through a bounded implementation revision, then rerun affected tests. The `execution_coordinator` must create or update exactly one product PR for every product repository changed by the run, using the approved branch and base, before commissioning `code_reviewer`; the reviewer examines that actual PR and its Test evidence. Address blocking findings within approved scope, retest, update the same PR, and request review again; escalate repeated or out-of-scope findings. Verify and record the PR URL, repository, base and head branches, commit, state, and Test/Review references. Never merge or approve your own work.

Write `execution_coordinator/execution-record-vN.md` (`EXEC-XXXX`) with unit status (`SUCCESS`, `PARTIAL_SUCCESS`, `FAILED`, `BLOCKED`, or `ESCALATED`), the verified product PR for every changed product repository, implementation results, Test and Review artifact references, fallback and budget warnings, rework, and open actions. Request orchestrator validation. Completion requires the routed implementation, required Test, independent Review, and a verified product PR—not merely a successful worker message. A product PR is `NOT_APPLICABLE` only when no product files changed, with that fact recorded; inability to create a required PR is `BLOCKED`.
